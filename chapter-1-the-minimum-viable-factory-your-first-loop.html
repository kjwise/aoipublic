Chapter 1 – The Minimum Viable Factory (Your First Loop)

Build a tiny loop: Terrain → Effector → Map → Validator.

You can have it running in about an hour. We’ll keep the vocabulary plain until you’ve seen it run, then we’ll name the parts so we can reuse them precisely.

Quick Bootstrap: MVF v0 (Map-Terrain sync)

i3-section-01-substrate

The Substrate (Map · Terrain · Ledger)

SDaC is practical when the system has three explicit surfaces: intent, runnable reality, and a deterministic evidence trail.

MAP
Intent surface
Mission objects, constraints, and acceptance criteria.
TERRAIN
Runnable reality
Code, configs, schemas, and policies your system actually runs.
LEDGER
Evidence trail
Append-only records of diffs, validator output, and decisions.

We’re going to build a weekend-grade factory that proves the
substrate:


    

  • one bounded surface of truth (Terrain — your source
files)
    • 

  • one versionable intent surface (Map — a spec, a
README)
    • 

  • one Effector that proposes a patch (writes a
diff)
    • 

  • one Validator that enforces alignment (a
deterministic gate)
    • 



That Validator is our first example of Physics:
deterministic constraints the Effector cannot argue with.


In MVF v0, intent is implicit: it’s hard-coded into CLI (command-line
interface) flags and Make targets. You can think of that as a “Mission
v0.” In Chapter 7, we promote it into a typed Mission Object you can
diff, version, and re-run.


This first loop is deterministic on purpose. It lets you see the
mechanics without keys, SDKs, or network calls. Later, you can swap in a
stochastic Effector and keep everything else unchanged.


What can go wrong (when
you add a model)


MVF v0 avoids model failure modes by design. The moment you replace
the deterministic Effector with a stochastic one, a few “Day 2” issues
might appear:


    

  • Malformed output: wrong format (not a diff), wrong
paths, or unparseable structure.
    • 

  • Scope creep: edits outside the allowed region or
touching unrelated files.
    • 

  • Invented structure: interfaces, routes, or fields
that never existed in the Terrain (a Map Contamination risk).
    • 

  • API failures: rate limits, timeouts, transient
errors.
    • 

  • Non-convergence: repeated retries that never reach
pass without circuit breakers.
    • 



Chapters 2 and 5 show the core mitigations: strict output contracts +
parsing, structured validator findings fed back into retries, and hard
stop conditions. Appendix B is a quick diagnostic atlas when the loop
misbehaves.


Fast path
(recommended): run the companion code repo


All runnable code for MVF v0 lives in the companion repo:
kjwise/aoi_code on GitHub.


First, clone the repository and run the full loop:


# Clone the companion code repo
git clone https://github.com/kjwise/aoi_code.git

# Enter the directory
cd aoi_code

# Run the sync + validate loop
make all


This command will first run the Effector
(sync_public_interfaces.py) to update the documentation
Map, then run the Validator
(validate_map_alignment.py) to confirm the Map and Terrain
are aligned.


You should see the following output, including a diff showing the
change to the documentation and a final pass signal from

What the tools do (interfaces
+ flow)


The two scripts are intentionally small and deterministic:


    

  • The Effector extracts a list of public function
signatures from the Terrain (product/src/) and rewrites a
bounded block under ## Public Interfaces in the Map
(product/docs/architecture.md). It emits a diff-first patch
and can apply it.
    • 

  • The bounded Map block is intentionally schema-like: a list of
backticked signatures under one heading. If you change that surface, you
change both the Effector’s rewrite and the Validator’s parse.
    • 

  • The Validator re-extracts those signatures from
the Terrain using a stricter parser than the Effector, checks the Map
block is well-formed, and returns pass/fail based on exact
match.
    • 



You now have a minimal loop that (1) senses drift, (2) proposes a
patch, (3) applies it inside a bounded Map surface, and (4) proves
Map/Terrain alignment with a deterministic Validator.


Re-run make all to confirm idempotence: the Effector
should report no drift detected and the Validator should
still pass.


The command panel:
make


In the companion repo, those scripts are already wired behind a
stable interface (make sync, make validate,
make all).


Expected output (after you’ve synced once) looks like this:


[effector] no drift detected (Map matches Terrain)
[validator] map_terrain_sync=pass


That’s the same loop, now behind a stable interface.


Why make shows up
in this book


In this book, make is the default command panel: one
stable command surface that humans, CI, and agents can all call. In
Chapter 7 we name this abstraction (the Driver Pattern);
make is the canonical Driver implementation for the book’s
substrate.


You can replace make with any task runner. The point is
the interface, not the tool:


If you’re a Bazel/Nx/Turborepo shop, mentally substitute your
monorepo task runner; Chapter 7’s Driver Pattern shows how to put a
stable command surface in front of whatever you already run.


    

  • Discoverable: make help can print a
menu of supported workflows.
    • 

  • Consistent: humans, CI, and agents all call the
same targets.
    • 

  • Swappable internals: you can replace scripts under
the hood without changing callers.
    • 



Hardening ladder: MVF
v0 → v0.2 → v0.5 → v1 → v2


The factory grows by adding Physics and governance, not by widening
autonomy. This ladder provides a practical path from a simple,
deterministic loop to a more robust, autonomous system.


    

  • MVF v0 (Weekend): This is what you’ve just built.
It’s a foreground loop with one narrow, deterministic Effector, one
Validator, and a clear trace of its work in the Git Ledger. It proves
the core mechanics are sound.
    • 

  • MVF v0.2 (Day 2): Use AI to help you author new
deterministic Effectors and Validators faster — but keep the runtime
loop deterministic.
    • 

  • MVF v0.5 (Week): Put your first stochastic model
call inside an Effector (Chapter 2’s Deterministic Sandwich), while
keeping the same hard gates and scope boundaries.
    • 

  • MVF v1 (Week+): Introduce explicit Mission
Objects (Chapter 7), which are structured, versionable requests
that replace implicit CLI flags. This makes runs replayable and
governable without changing the Physics.
    • 

  • MVF v2: With a reliable loop and explicit missions,
you can now scale its operation. This involves scheduled runs via a
Dream Daemon (Chapter 9) to perform background
maintenance, building Map-Updaters (Chapter 8) to keep
more complex documentation in sync, and establishing Immutable
Infrastructure (Chapter 10) to create protected boundaries that
even the system itself cannot change.
    • 



Naming the parts (the canon)


You just ran an Effector and a Validator against a real boundary. In
SDaC we give these pieces names so we can reason about them and build
tooling around them.


    

  • product/src/ → Terrain (runnable
reality)
    • 

  • product/docs/architecture.md → Map
(versioned intent surface)
    • 

  • Git → Ledger (the history of diffs and
decisions)
    • 

  • sync_public_interfaces.py → Effector
(proposes/applies a patch)
    • 

  • validate_map_alignment.py → Validator
(enforces pass/fail)
    • 



You do not need all of these terms on page one. You can keep thinking
“code / doc / change script / check” for now. But the canonical names
will show up throughout the book.


Terrain = code (runnable
reality)


The product/src/ directory is our
Terrain: the code that actually runs.


Map = versioned intent
surface


The product/docs/architecture.md file is our
Map: a structured representation of the Terrain that we
can keep aligned.


Version control = Ledger
(audit trail)


Git is the Ledger. Every commit records a
transaction: what changed, when, and by whom. In a real SDaC system,
each automated run also records provenance: which Mission Object, which
inputs, which validators, and which outputs.


Effector = bounded change
proposer


The sync tool is an Effector: it observes Terrain
and proposes a patch to a Map surface. Later, you can put a model call
inside an Effector, but the contract stays the same: output a diff, then
prove it admissible.


Checker = Validator
(blocks bad changes)


The validator script is a Validator. It validates
alignment between Map and Terrain. If it fails, the diff is blocked. No
debates. No “looks fine.”


The Loop in Action


What you’ve built is a fundamental loop:


    

  1. Edit the Terrain: you change code in
product/src/.
    2. 

  2. Run the Effector: make sync
proposes/applies a patch to the Map surface in
product/docs/architecture.md. A git diff shows
the change.
    3. 

  3. Run the Validator: make validate
enforces whether Map and Terrain are aligned.
    4. 

  4. Diff & gate: If the validator passes, you
can commit the change to the Ledger. If it fails, the change is blocked
and you refine.
    5. 



This loop gives you deterministic context (the Map), deterministic
gates (the Validators), and verifiable loops (the Git Ledger and CI
feedback). It tames the stochastic nature of GenAI by wrapping it in
engineering rigor.


If you want a frame: it’s recursive self-improvement (RSI) for
programming, with the recursion bounded by Physics and recorded in the
Ledger.


At this point, you have a working factory. It’s minimal, but it
demonstrates the core components.


Where this leads: in Chapter 13 (The Hofstadter Bridge), we take this
same pattern (one bounded block + one Effector + one Validator) and
apply it to documentation itself. That “micro-loop” is the smallest step
toward making parts of the Map enforceable instead of merely
advisory.


SDaC doesn’t require knowing the destination up front. It requires
knowing what a safe iteration looks like (also Chapter 13).


Actionable: What you can do


    

  1. Run MVF v0 (recommended path):
    

    cd aoi_code
make all
    

    If you want a clean baseline between runs:
    

    git restore product/docs/architecture.md
    2. 

  2. Break it (create drift):
    

      

    • Add a new public function to
product/src/tax_calculator.py (for example
def tax_rate(country: str) -> float: ...).
      • 

    • Run only the validator:
      

      make validate
      • 

    

    It should fail with missing_in_map=[...].
    3. 

  3. Fix it (restore alignment):
    

      

    • Run make sync and then make validate
again.
      • 

    • Inspect the diff:
      

      git diff
      • 

    

    If the diff touches more than you intended, treat it as a
blast-radius failure. Appendix B has a quick diagnostic for “slice too
large / too small” (even when you’re not using an LLM yet, the failure
shape is the same: too much context or too much freedom produces
surprise edits).
    4. 

  4. Harden one step:
    

      

    • Add one more Validator (formatting, type checks, or a schema
Validator) and make all depend on it.
      • 

    5. 



This is the shape of the Minimum Viable Factory: small blast radius,
concrete diffs, and pass/fail gates.
