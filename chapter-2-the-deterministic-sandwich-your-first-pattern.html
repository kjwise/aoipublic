Chapter 2 – The Deterministic Sandwich (Your First Pattern)

Chapter 1 traced a minimal loop that stayed in bounds because every step was deterministic. This chapter shows what changes when one of those steps uses a foundation model.

Start with one failed attempt and one correction. Deterministic Prep extracts the exact Terrain signatures and the only Map block the run may change. The first model attempt adds annotations that are absent from Terrain, so deterministic Validation rejects the candidate and returns that exact mismatch.

On the second attempt, the model uses the extracted signatures without invention. Validation confirms correspondence and scope, then seals the proposal. A separate adoption step rechecks the current Map state before applying it.

This is the Chapter 1 loop with a different worker. Intent, scope, evidence requirements, routing, sealing, and separate adoption stay fixed; candidate generation becomes probabilistic. The Validator is still decisive for this one-property loop because each evidence class has one declared destination. That is the whole pattern in miniature: one probabilistic step pinned between deterministic layers.

That loop can propose a diff and stop on PASS/FAIL. To include a model safely, it needs the same deterministic boundaries. Large language models (LLMs) drift. Ask for the same task twice and you can get a different diff. In production, that variance is where regressions hide.

Longer instructions alone are not the fix. The architectural fix is structure: Prep -> Model -> Validation. That structure is the Deterministic Sandwich.

The Deterministic Sandwich: Prep, Model, Validation

The Deterministic Sandwich is the simplest reusable pattern for bounding one probabilistic invocation in a production loop. The pattern has three parts. In this teaching case, the invocation is one model call inside the Effector, pinned between two deterministic layers:

i3-section-03-deterministic-sandwich

  1. Prep: A deterministic setup layer. It normalizes the request, builds a bounded context slice, and keeps untrusted evidence separate from actual instructions. It takes structured data and produces a structured model request.

  2. Model: The single bounded model call. In this minimal sandwich, it is the only unpredictable step, so you keep its surface area small.

  3. Validation: A deterministic gate. It strictly parses the model output and runs Validators. It accepts the output only if it matches the rules you defined.

Think of it like building a reliable wrapper around a flaky external service. You control what goes in, you control how you read what comes out, and you reject anything that breaks the contract.

Prep and Validation are both deterministic, but they guard different boundaries. Prep controls inputs; Validation controls outputs. The model remains one bounded Effector between them.

Deterministic execution does not imply a complete specification. A Validator can return the same answer every time and still check the wrong rule or miss an important case. Chapter 3 owns that problem; here the requirement is simply that the model cannot bypass the checks that exist.

1. Prep: Build the request deterministically

Prep reads the fixed work contract—formalized in Chapter 7 as an activated Mission Object—and builds the same request shape from the same inputs. It tags repository content, tickets, logs, chat, and prior findings as provenance-bearing evidence rather than instructions. Mixing those channels lets hostile or accidental prose compete with the actual rules.

For the Chapter 1 doc sync, Prep needs only the extracted signatures, the permitted Map block, and any normalized Validator finding. Start from that anchor, add direct dependencies, and prune everything else. Extract structural facts such as signatures and routes deterministically; let the model generate only bounded content around that skeleton.

The failure mode is Map Contamination: invented structure enters a Map, then later runs consume the invention as fact. Prevent it by comparing the candidate skeleton with a fresh deterministic extraction and failing on mismatch.

2. Model: The probabilistic step in the minimal sandwich

Within this minimal sandwich, candidate generation is the only probabilistic step. Ask for a declared shape, such as a unified diff or strict JSON, and treat the result as an untrusted candidate.

That is a property of this teaching pattern, not a rule that larger workflows contain only one probabilistic step. A larger workflow may arrange several such steps sequentially, conditionally, or in parallel.

3. Validation: The hard gate

Validation parses the output strictly, checks its schema and semantics, and rejects the whole candidate on any failure. No regex repair or partial application. A stable finding identifies the governed property, the affected surface or location when available, a machine-readable reason, and the evidence supporting it. Chapter 3 owns that finding contract; Chapter 5 owns retry and stopping policy.

The failed first attempt in this trace shows why the finding must name the exact mismatch without changing target or scope. A later attempt may receive that finding as evidence, but Chapter 5 owns the retry and stopping policy.

Beyond One Model Call

To extend the Sandwich to larger systems, distinguish a workflow from a loop. A workflow is the finite governed graph of steps. A loop is the declared repetition of a step, a subsequence, or the complete workflow. Continuous operation is therefore a sequence of finite runs with fixed authority, terminal outcomes, and sealed evidence, not one immortal run whose state and rules drift indefinitely.

A step may invoke a model or tool directly, or it may invoke an agent harness through a command-line interface (CLI) or application programming interface (API). The CLI or API is the invocation and control surface, not a separate kind of worker. An agent harness surrounds model-and-tool work. Within its declared inputs and read authority, it manages working context, tool use, bounded internal iteration, and result production. Thus make lint can expose a deterministic check through a CLI, while a Codex CLI invocation can expose a coding-agent harness rather than a single deterministic command.

A harness names a role at a boundary, not a fixed architectural layer. From the enclosing workflow’s viewpoint, it is one bounded component. The activated Mission fixes the step’s authority, permitted effects, budget, and required evidence; the workflow governs its transitions and the results it may consume; the protected runtime enforces those boundaries. An agent harness may invoke smaller harnesses, but authority does not implicitly propagate: each nested component remains inside the authority granted at its enclosing boundary, and its result cannot confer new authority. Classify the step by its declared behavior, effects, and evidence contract rather than its invocation surface.

A component with its own finite governed lifecycle and sealed result can act as a child workflow. Otherwise, its outputs and attempted effects remain untrusted at the parent boundary.

Several such steps can form a chain across representations: intent into a work contract, a contract and Context Packet into a code candidate, or formal artifacts into proposed documentation. Each step proposes only its declared transformation. Its output contract and independent checks determine which correspondence claims the enclosing workflow may rely on.

Larger workflows may also use model-based Validators or Judges. Deterministic runtime boundaries still enforce evidence, scope, budgets, allowed transitions, and separate admission.

When Slicing Goes Wrong

The previous example assumed good context. Here’s what it looks like when the slice is bad.

If Prep includes the whole source tree and document, the model may update the right block and rewrite adjacent material. The scope Validator makes the slicing error visible by reporting that the candidate touched both the permitted interface block and an undeclared notes section.

The diagnosis is not “bad model behavior.” The slice included adjacent material that looked like instructions or editable scope even though the task did not authorize changes there. Change the slice: include only the extracted skeleton and allowed edit region. Chapter 6 names the broader context-quality objective and develops the full method.

When the Pattern Is Worth It

The Sandwich is worthwhile when work repeats, persists, has material blast radius, crosses team boundaries, or can be judged by an actionable invariant. A temporary artifact with a cheap and direct acceptance signal may need only generation and inspection. A persistent capability with hidden obligations needs stronger boundaries.

Start with one bounded Effector and one gate. Add structured findings when retries become useful, a Mission when multiple tasks or operators need stable authority, and templates when request drift becomes a real failure mode. Generated scaffolding is cheaper than it used to be; ownership, calibration, and false positives still cost engineering time.

AI is especially useful when mature libraries or services already contain the difficult implementation logic and stable interfaces constrain the connecting work. Direct checks can grade the declared composition. The probabilistic step does not need to reproduce every internal detail; it needs to connect the components within their contracts and the workflow’s effect boundary.

The reusable asset is the control surface. New workflows can replace the extractor and Validator while preserving the output contract, evidence shape, and stopping policy. Tooling may differ by stack; the boundary does not.

The Sandwich is therefore more than a safe model wrapper. Its stable contracts let it become a dependable step in a larger workflow. A malformed output or out-of-scope effect must fail before application; only the candidate may vary while the surrounding authority, checks, and evidence contract remain fixed.

The organizational consequence is that proposal volume can increase without giving every proposal a direct path to production. The surrounding process, rather than the probabilistic step, continues to determine what evidence is required and what may advance.
