Chapter 7 – Intent as Code (Mission Objects)

A serious workflow needs more than an instruction string. It needs a versioned work contract that states what the work is, what may define correctness, what may change, what evidence is required, when execution must stop, and who may admit the result.

The formal name for that contract is a Mission Object. A mission is the abstract objective, such as “document the /v2/users endpoint.” The activated Mission Object is the exact, immutable authority for one run.

Contract part What it fixes Example
Objective The intended outcome Document /v2/users in the service README
Authority The adopted sources that may define the governed property The fixed OpenAPI path definition
Effects Writable, read-only, and prohibited surfaces Edit one README block; do not touch code, policy, or CI
Outputs and checks What must exist and which independent checks must pass A bounded README candidate whose route inventory matches the contract
Stopping and admission Budgets, failure routing, approval, and the separate path by which a proposal may become effective Stop after three attempts; docs-owner review admits the patch

Before activation, a Mission Object is only a proposed work contract. Independent approval or adopted policy must activate its exact identity before it authorizes execution. Parsing proves only that the object has the required structure. It does not prove that the intent is correct or grant permission to execute it.

Part II established why candidate generation needs bounded context, comparable evidence, and finite stopping. The Mission Object packages those decisions so the same class of work can run repeatedly without reconstructing authority from tickets, chats, or prompts.

What Belongs in the Contract

The categories in the opening table serve different purposes.

The objective names the outcome without prescribing every implementation move. Authority identifies the adopted contracts, policies, or decisions allowed to define correctness for the governed property. Read access does not confer authority: a source may be relevant evidence while remaining unable to instruct the run.

Effects bound where and how work may occur. They include writable regions, denied paths, external systems, network access, credentials, and any behavior the run may not perform. Outputs and checks define what the workflow must produce and how selected properties will be evaluated. “Fast enough” is not an executable condition; a fixed workload, environment, measurement protocol, threshold, and tolerance can be.

The contract also fixes when execution must stop and what may happen afterward. Stopping and admission name the budgets, permitted routes, required approvals, and response to missing evidence. A missing contract may require an external decision. Exhausted attempts without progress should end as an evidenced failure. A successful run closes a proposal; it does not merge, deploy, or adopt it.

If a criterion cannot produce evidence under a declared decision protocol, keep it as an explicit human review item or a deferred quality goal. Do not hide subjective judgment behind a field that looks machine-readable.

Authority and Evidence Are Different Artifacts

One mutable document cannot safely serve as both instruction and history. A governed run uses two related artifacts:

Artifact Role
Mission Object Fixed authority: objective, authoritative sources, effects, outputs, checks, budgets, routing, and admission policy
Run Record Append-only execution evidence: baseline, bounded input, attempts, findings, actual effects, decisions, outputs, budgets, and sealed result

The Run Record is the evidence record for one execution. Findings may guide the next attempt or support a later Mission proposal, but they cannot rewrite the active Mission. A changed objective, writable scope, budget, check plan, or admission rule requires a new Mission version and a new activation decision.

The same separation applies to outputs. A workspace output, such as the edited README, is part of the candidate. An evidence output, such as the protected Map-alignment report, is retained because the Mission or policy declares it necessary for reconstruction or decision. A workflow should not copy every generated file into its evidence store. Declared output checks must finish before the proposal can close, but retaining an artifact does not make it authoritative or admit it.

Draft, Activate, Execute

A human, planner, Sensor, or model may draft a Mission Object. Drafting is assistive, not authoritative. Independent activation must fix the exact version permitted to run and record the approval basis.

An ordinary-language request may seed that draft. A model can turn “document /v2/users without changing code” into proposed fields for the objective, authority, effects, checks, budgets, and admission path. The structured proposal makes omissions and conflicts easier to inspect; it does not make guessed fields authoritative. Activation must verify that the contract reflects adopted intent before execution.

Before execution, protected preflight resolves the exact authority and check identities, pins the source baseline, and verifies that declared outputs fit the effect boundary. In a repository workflow, this may mean resolving an OpenAPI contract digest, a Git base commit, and a protected CI check. Preflight rejects missing or ambiguous decision mechanisms and never accepts executable graders supplied by the candidate.

Once activated, the Mission remains fixed for the run. The workflow may choose only among its declared transitions. It cannot widen scope, add a grader, change a budget, reinterpret missing evidence as success, or authorize admission. Those are changes to authority, not refinements of a candidate.

A later Mission version may supersede the contract for future runs. Existing Run Records continue to refer to the exact version that governed them.

Checks Bind to the Candidate

Chapter 3 defined structured findings, and Chapter 5 defined bounded routing. The Mission Object binds those mechanisms to one run. It names the required protected checks, while each report identifies the exact candidate and configuration it evaluated.

Only complete, internally consistent evidence from the declared check set may support a transition. A finding may enter the next bounded input as tagged evidence. It cannot become a new instruction, expand authority, or substitute for a check that did not run.

This is also why candidate-proposed tests are supporting evidence rather than the sole oracle for that candidate. They may improve coverage, but the active Mission and protected policy decide which checks count.

Reuse Without Self-Authorization

Templates can predeclare the shape of recurring work: default budgets, permitted check identities, routing, and output classes. Specialization still supplies the exact objective, authority, effects, and evidence requirements, then passes independent activation.

A rejected candidate may contain a useful fragment. That fragment remains untrusted. A later run may reuse it with provenance, but it must re-enter as part of a new candidate inside declared scope and pass the ordinary checks and admission path. Salvage does not promote failed work.

The same rule governs recursively proposed work. A maintenance scan may produce a draft Mission, and run history may suggest a better template. Neither becomes authority until a separate activation or adoption decision approves the exact proposal.

The Mission Object is therefore not a detailed ticket and not a prompt wrapper. It is the stable boundary between requested work and executable authority. Together, the two records make the change process inspectable and reusable as structured data. The Mission Object states what may happen; the Run Record preserves what did happen. The system can then reuse the workflow without asking a model to infer permission on every run.

The organizational consequence is repeatable delegation. Teams can approve a stable class of work once, then let each instance execute under the same explicit authority and evidence contract instead of reconstructing permission and review expectations from prose.
